## 一、学习路线

> 主线参考：**能跑起来 > 能看懂 > 能自己造**。每步都有对应的东西在仓库里。

### 1. HTML / CSS / JavaScript（基础，已完成入门 ✅）

- 能看懂根目录 `index.html` 的每个标签、`css/style.css` 的每个选择器
- 能理解 `js/main.js` 里的主题切换、hash 路由、文章筛选这些交互逻辑
- 能理解 `js/content.js` 的空框架结构，并自己加一篇文章 / 一个项目
- **验收**：不用看文档，能自己给网站加一个模块

### 2. 内容维护（进行中 🔥）

- 用 Markdown 写一篇真实文章 → 放进 `articles/` → 在 `js/content.js` 登记 → 推送上线
- 在 `js/content.js` 登记第一个真实项目
- 在计划页「年 / 月 / 日」三视图里记录自己的日常计划
- **验收**：网站「文章」页有你的第一篇真实笔记，「项目」页有你的第一个真实项目

### 3. React / Vite（未来方向，先不急 🔭）

- 本项目为了 GitHub Pages 的「零构建」特性，用的是原生 JS
- 等原生 JS 熟练了，再学 React / Vite 会更轻松：
  - 理解「组件化」：把页面拆成一个个小组件
  - 理解「数据驱动」：改数据，页面自动变
- **验收**：能用 Vite 起一个能跑的小项目

### 4. Python / FastAPI（计划中 📌）

- 先在本地把 Python 基础练熟：变量、列表、字典、函数、文件读写
- 再学 FastAPI：理解「路由 / 模型 / schema」三个概念
- `docs/learning-notes.md` 里有之前全栈阶段留下的 FastAPI 笔记
- **验收**：能写出一个返回 JSON 的小接口

### 5. 数据库（计划中 📌）

- 先用 SQLite（零安装），理解「表 / 记录 / 查询」
- 再升级 PostgreSQL：理解「服务进程 + 连接字符串」
- **验收**：能给博客系统加「标签」表

### 6. GitHub Actions（进行中 🔥）

- 本项目已经在用：`.github/workflows/ci.yml`，每次 push 自动跑 `scripts/check.py`
- 理解「每次 push 自动执行一段脚本」这件事
- **验收**：故意改坏一个文件，看 CI 变红

### 7. 部署（计划中 📌）

- 静态主页已经在 GitHub Pages 上了 ✅
- 前端未来可部署到 Vercel / Netlify，后端可部署到 Render / Railway
- 详见 [deployment.md](deployment.md)

## 三、未来在线编辑功能（规划）

> 当前版本的内容全部通过 **GitHub 仓库**维护：写 Markdown → 放进 `articles/` → 在 `js/content.js` 登记 → `git push` 上线。
> 没有后台、没有数据库、也没有登录系统——访客只能看公开内容，站长靠仓库改文件。
>
> 如果未来想「登录后在网站里直接编辑文章和计划」，需要把本站从纯静态升级为带「在线编辑」能力的版本。
> 以下是三种可选方案（按实现复杂度从低到高）：

### 方案 A：Decap CMS + GitHub 登录（最接近现状，改动最小）

- 在仓库里加一个 **Decap CMS（原 Netlify CMS）** 管理入口（纯静态，仍托管在 GitHub Pages）
- 站长通过 GitHub 账号登录后，在网页里编辑文章 / 计划，CMS 自动把改动**提交成 commit 推回仓库**
- 不需要自建后端；文章仍是 `articles/` 下的 Markdown 文件，数据结构基本不变
- 适合：想先在网页里写东西、但不打算维护服务器的阶段

### 方案 B：GitHub OAuth + GitHub API 提交文件（自研轻量方案）

- 前端页面弹 GitHub 授权（OAuth），拿到 token 后调用 **GitHub Contents API** 直接读 / 写仓库里的文件
- 本质上还是「用网页帮你 commit + push」，底层仍是 Git 仓库
- 需要自己写 OAuth 换 token、写文件、处理冲突的代码；token 要保护好，**不能明文存在前端 / localStorage**
- 适合：想完全自研、不想依赖 CMS，但能接受自己维护授权逻辑

### 方案 C：FastAPI 后端 + 数据库 + 登录系统（真正的全栈）

- 搭一个真正的后端（如 FastAPI）+ 数据库（如 SQLite / PostgreSQL）+ 账号密码 / OAuth 登录
- 文章、计划、项目存在数据库里，网页通过 API 读写
- 需要额外部署后端服务（Render / Railway 等），也要自己处理密码安全（哈希存储）、权限控制、备份
- 适合：已经学完后端和数据库，想把网站升级成真正的全栈应用

### 当前阶段的立场（重要）

- **本站目前不实现「假登录」**——没有后端、没有数据库，做一个假的登录框没有任何意义，只会误导访客
- **不在前端保存密码**——即便将来接入真实登录，密码也应走 HTTPS + 后端哈希校验，绝不能明文存在前端 / localStorage
- 在真正具备后端能力之前，内容维护仍以 **GitHub 仓库 + git push** 为主，安全、清晰、可追溯
